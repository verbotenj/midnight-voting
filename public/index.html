      PASSPORT → ELIGIBILITY / NFC ENGINEERING

      Read the chip. Then ask if the document is still valid.

      NFC is the short-range radio link between a phone and a passport chip. The document number comes from the signed document data—not from the chip’s radio identifier. This web app animates fictional reads only; it does not read a real passport.

      01 / CONNECT LOCALLY

      Establish a secure session

      A native reader uses access information from the document, commonly its machine-readable zone (MRZ), to establish BAC or PACE as supported. Ask for consent, show where to hold the phone, and handle a moved or unsupported chip without issuing anything.

      02 / AUTHENTICATE

      Read only what policy needs

      DG1 contains document and holder details. SOD contains signed data-group hashes. Validate the signature with trusted issuer certificates and compare the required hashes. DG2 is the facial image: skip it for this POC. Chip authentication is a separate anti-copy check where supported and required.

      03 / CHECK THE AUTHORITY

      Authentic is not currently valid

      An authentic old passport can have been replaced or cancelled. documentStatus comes from an authoritative status service, not a live field on the chip. Our authority returns REVOKED for DEMO-P003 and refuses a credential even after a successful simulated chip read.

      What must we build for real NFC?

      A native mobile reader with ISO-DEP/APDU access, secure messaging, document parsing, certificate trust management and a status-service integration. Browser Web NFC only handles NDEF messages; it does not provide the low-level interface needed here. Merely detecting NDEFReader does not make a passport reader.

      Keep raw document bytes inside the native verifier. Send only policy-required information to the authorized eligibility service, never to Midnight. Release document buffers promptly and exclude MRZ, photographs and NFC dumps from storage, analytics, crash logs and screenshots. Real-device testing is still required; Playwright cannot validate a chip.

      SIMULATOR → MIDNIGHT PREVIEW / IMPLEMENTATION PLAN

      A real ballot needs a contract, not just a transaction.

      The separate live runner has deployed the Compact contract, enrolled two credentials, finalized two real Preview votes and closed at YES 1 / NO 1 using DUST. The ballots on the Demo page still run in a local simulator. A voting credential is a secret-backed entitlement, not a transferable NIGHT token. Visit Live Preview for chain evidence.

      1. Compile the actual voting rules · implemented.

        The deployed Compact contract enforces election scope, authority-only eligibility updates, a frozen eligibility root for voting, one-time nullifiers, YES/NO counts and authority-only close. A witness supplies the private secret and Merkle path. Eight compiled-circuit tests check the rules; network receipts provide separate evidence of accepted transactions.

      2. Make issuance durable and separate.

        Keep the identity registry off-chain. Atomically reserve one issuance per identity and election, publish its commitment through an authorized transaction, and mark it issued only after finality. Store a pending receipt so retries reuse the same commitment instead of issuing twice.

      3. Prove locally, then submit.

        Use compatible Compact, Midnight.js, wallet and prover versions. The device proves membership and the election-specific nullifier; only proof-bound public data reaches the network. Remove the simulator’s credentialSecret HTTP vote payload entirely. Never send witnesses to an untrusted prover.

      4. Confirm the exact transaction and state.

        Show build → prove → sign → submitted → finalized separately. Save the transaction identifier before broadcasting, reconcile uncertain submissions without blind retries, and read the deployed contract’s root, nullifiers and tally back from the indexer. Animation completion is not confirmation.

      5. Full Preview ballot · verified separately.

        The runner enrolled both valid credentials before opening, finalized YES and NO, and closed at 1–1. The authority refused duplicate and revoked-document requests. Preview rejected a modified-proof transaction; duplicate and post-close votes were rejected during local circuit construction, without broadcast. The new live panel checks real receipts and offers guarded steps for unfinished elections. A fresh complete UI broadcast run is still unverified; animation and fixture tests are not network tests.

      Privacy checkpoint before deployment

      Never derive a public commitment from the passport number. Use a fresh random secret per election and bind it to the contract/election. Issuing and immediately voting as the only eligible voter defeats the anonymity set; real flows need an enrollment phase. A changing public tally exposes each vote choice, and wallet, IP and timing metadata can link it to a person. Stronger privacy needs a reviewed submission and tally design—not merely “ZK enabled.”

      UNDER THE HOOD / ZERO-KNOWLEDGE

      Prove you may vote. Don’t reveal who you are.

      A zero-knowledge (ZK) proof is cryptographic evidence that a statement is true, without revealing the private information used to prove it. Think “I have a valid voting credential,” without showing which credential is yours.

      WHAT THE COMPACT VOTING PROOF ESTABLISHES

      “I know the secret behind an eligible credential in this election’s Merkle tree, and this nullifier is correctly derived from that secret and this election.”

      01 / PROVE · PRIVATE

      The computational work

      A trusted local prover uses the secret and Merkle membership path (the private witness) to generate a proof. Circuit complexity, hardware and first-time key loading affect how long it takes. Never give a witness to an untrusted proof service.

      02 / VERIFY · PUBLIC

      A much smaller check

      Midnight uses zk-SNARKs, designed for small proofs and efficient verification. The intended contract checks the proof, rejects a used nullifier, and updates the tally only while the election is open.

      03 / CONFIRM · NETWORK

      Waiting is not all proving

      Wallet approval, proving, submission and block finality are separate waits. A slow transaction does not tell us which step is slow. We must measure real executions, not animation duration.

      So, are ZK proofs slow in this demo?

      The browser animation does not run a real voting proof. Its animated proof and 1-second authority check are teaching delays, not benchmarks; the simulator sends the secret to its local server. The separate Preview runner uses the compiled Compact circuit and trusted loopback prover. Its build/prove, DUST balancing, submission and finality stages are real waits—not a fixed animation timer.

      What does ZK not prove or hide?

      The authority—not the proof—checks document status and issues one credential per demo passport. Passport chip data alone does not establish current revocation status. ZK does not prevent timing or wallet-address correlation. A live tally with one vote at a time can reveal each vote’s choice; batching or a private tally design and separate submission infrastructure need further work. This POC does not prove end-to-end election anonymity.
